# Receipts — every entry is a mistake that actually happened

All from the 2026-08-18 manual sweep (13 PRs across two GitHub owners) unless marked otherwise.
Retract in place if one turns out wrong; never silently delete.

## 1. Cron-swept branches — the diff is not the work

**Verified 2026-08-18:** a skills-repo PR claimed to add one skill (13 files) but
showed 66 files CONFLICTING — the daily inventory cron's bare `git push` had swept
~60 unrelated commits (many duplicated by a replay) onto the branch. Fix: rebuild
as `origin/main` + only the commits the PR is about. **Gate before force-pushing
the rebuild:** every dropped commit must exist on at least one other ref
(`git branch -r --contains <sha>`) — in this case all were on 4+ other branches.
If any commit is unique to the branch, preserve it (backup ref) first.

## 2. Vacuous verification — verify by loading, not by diffing a maybe-no-op

**Verified 2026-08-18:** an index generator run as `apply.sh <lib> --apply --only manifest,index` silently
matched NO stage (`--only` is exact-match, one stage per flag) and regenerated
nothing; the follow-up "diff is identical → artifacts current" receipt was
therefore proof of nothing. Meanwhile the "current" MANIFEST didn't even parse as
YAML. Rules: (a) one `--only` stage per invocation; (b) a freshness receipt must
include a positive signal the generator RAN (its output naming what it wrote);
(c) machine-readable artifacts are verified by loading (`yaml.safe_load`), never
by "byte-identical to a maybe-no-op". When a receipt is found vacuous, correct it
in a visible PR comment — don't quietly re-verify.

## 3. Pre-existing CI failure — root-cause in its own PR, then carry it in

**Verified 2026-08-18:** an app repo's `audit` check (npm audit, 9 vulns) failed
on every PR AND on main — no PR could go green. Fixing deps inside a content PR
is scope-mixing; documenting the failure leaves the queue red. The move: fix the
root cause in its own PR (#216: next 16.2.7→16.3.1 + `npm audit fix`; verify
locally — audit exit 0, tsc, tests, build), open it ready, then `git merge` that
branch into the blocked PR so it goes green immediately; its diff collapses back
to content-only once the fix PR merges.

## 4. Fold before closing as superseded

**Verified 2026-08-18:** two app-repo PRs (stale weekly reports) were superseded
by #215 — but their log entries had never landed on main, so #215 was stacking on
a placeholder. Closing them first would have lost two weeks of content. Fold the
superseded PRs' content into the successor (one commit, named in the close
comment), then close. "Superseded" must be made true before it is declared.

## 5. The mid-flight guard

**Verified 2026-08-18:** a templates-repo PR appeared DURING the sweep, authored
by a session that was simultaneously pushing generator fixes to a sibling repo.
Its work overlapped ours (same MANIFEST quoting defect). Touching it — flipping,
pushing, "helping" — would have collided with a live session. Detector: updated
within ~2h, or sibling branches moving. Disposition: untouched, named in digest.

## 6. Enumeration across both orgs in one query

**Verified 2026-08-18:**
`gh search prs --draft --state open --owner <your-user> --owner <your-org> --json repository,number,title,updatedAt,author`
returns the full cross-org draft set in one call. Ready-but-red needs a second
pass per repo (`gh pr list` + `statusCheckRollup`). `gh pr view N --repo X` at act
time is the state re-check — search results go stale mid-sweep (two of today's
finds merged while the sweep ran).

## 7. Generated-artifact PRs collide with their own stack

**Verified 2026-08-18:** three sibling PRs all regenerated the same
MANIFEST/README → serial conflicts, order-dependent.
When a PR's conflict is in a *generated* file, resolve by taking the base branch's
copy and re-running the generator on the resolved tree — never hand-merge
generated bytes. Then note in the receipt comment that whichever sibling merges
second is a one-command regen.

## 8. Headless sessions and plan mode (house gotcha, inherited)

**Verified in another scheduled harness:** if user-level settings default to plan
mode, a headless `claude -p` run can never exit it — it writes a plan file instead
of acting. Every cron invocation must pass
`--permission-mode default` plus its scoped settings file.

## 9. A lockfile is NOT a fully-derived artifact — §7's rule breaks on it

**Verified 2026-08-21:** an app-repo PR's only conflict was `package-lock.json`.
Applying §7 (take the base branch's copy, re-run the generator) produced a lock
that **reintroduced 6 vulnerabilities — 1 moderate, 5 high** — and `audit` went
from green to red. The branch's npm-audit fixes lived *in the lock*, as transitive
pins that its `package.json` cannot reproduce: regenerating from the base threw
them away and `npm install` had no reason to put them back.

§7 holds for artifacts whose every byte derives from tracked source (a generated
README index, a MANIFEST built from frontmatter). A lockfile is only *partly*
derived — resolution is an input too. Rule: when the conflicted generated file is
a lockfile, take **the side that carries the fix** as the base, regenerate to
absorb the other side's new deps, then prove it by running the gate
(`npm audit --audit-level=high`, `npm ci`) rather than trusting the method. Check
both sides survived by name: here `next@16.3.1` (the PR's fix) and `pg@8.23.0`
(staging's new dep).

Corollary, and §2 again: the first `npm audit` was run on a tree that still had
conflict markers and returned a meaningless exit 0. Grep for
`<<<<<<<` before believing any gate you run mid-merge.

## 10. `mergeable: UNKNOWN` means "ask again", not "not conflicting"

**Verified 2026-08-21:** the night's queue said 10 stuck and "0 are deferred".
Re-enumerating at the end of the run — after the sweep had queried every PR, which
warms GitHub's cache — returned **seven more** in the app repo,
every one CONFLICTING since 2026-08-19, none of them ever in the queue.

GitHub computes `mergeable` lazily. A first `gh pr view` on a PR nobody has touched
recently returns `UNKNOWN` while a background job resolves it. `enumerate.py`
tested `== "CONFLICTING"`, so `UNKNOWN` appended no reason and the PR was
`continue`d — dropped silently, which is the failure this whole routine exists to
prevent, in the sweep's own harness. Fixed in the enumerator: poll until it
resolves, and report an unresolvable one as `mergeable-unknown` rather than
dropping it.

Two general lessons. **Any** `gh` field that can return `UNKNOWN` needs a re-poll
before a negative conclusion is drawn from it (`mergeStateStatus` is the other
one). And an enumerator that can drop a row must say what it dropped — a count
that only reports what it found reads as coverage.

## 11. Check for an existing PR before opening one for the same payload

**Verified 2026-08-21:** I opened a skills-repo PR (#28) to land 68 cron-swept commits,
then found #10 was already the deliberate holding PR for exactly that work — its
body even said "no further commits should be added to this branch." Wasted effort,
and briefly two PRs for one payload.

Cheap and it was skipped: read the bodies of the *other* enumerated PRs in the same
repo before opening anything, because the swept-work PRs cross-reference each other
(#10 named #18 and #19 as its own splits — both already merged, which is what made
it safe to close). Recovered by verifying #28 was a true superset — every unique
commit on #10 either landed via the merged #19/#18 or was an apply/revert net-zero,
and main's `find-meeting-time/SKILL.md` was byte-identical to #28's — then closing
#10 rather than leaving a duplicate. §4's "make superseded true before declaring
it" applies to a successor *you* just created, too.

## 12. A git command that fails is silent unless you check it — twice in one run

**Verified 2026-08-21 (run 2).** Two different helper scripts in the same sweep
"succeeded" while doing nothing, and in both cases the push that followed exited 0.

- `git merge --no-ff <branch> -F -` with the message on stdin. `git commit -F -`
  reads stdin; **`git merge -F -` does not** — it fails with
  `error: could not read file '-'`. Under `set -uo pipefail` (no `-e`) the script
  sailed on, the follow-up `git diff --diff-filter=U` found no conflicts *because
  no merge had been attempted*, and three PRs were reported as carrying a fix they
  did not carry.
- `git reset --hard <other-branch>` to "switch" branches. It moves **the currently
  checked-out branch** to that commit; it does not check the other branch out. So
  three PRs' resolution commits all landed on the branch left over from the
  previous iteration, and `git push origin prN:remote-branch` pushed an unchanged
  ref — printing `Everything up-to-date` and exiting 0.

Rules: pass commit/merge messages as a **file**, never `-F -`, and `|| die` every
git invocation. Never use `reset --hard` as a checkout — `git checkout -q "$BR"`
then assert `[ "$(git branch --show-current)" = "$BR" ]`. And a push is not
evidence: assert the postcondition you actually wanted —
`git merge-base --is-ancestor <what-you-merged> HEAD`, plus a diff of directories
present on the base but missing from the merged tree. Both bugs were caught by that
ancestry assertion and by nothing else; `mergeable=MERGEABLE` was true throughout.

## 13. Check whether a red check can even RUN before carrying its fix in

**Verified 2026-08-21 (run 2).** Receipt #3 says: fix a pre-existing CI failure in
its own PR, then carry that branch into the blocked PR. True — but only where the
check actually fires. `board-smoke` on the app repo is `pull_request:
branches: [staging]` with an explicit `paths:` list, and its own header says
"NON-REQUIRED job by design: never referenced by branch protection". Of tonight's
four PRs, only #196 touches a path in that list (`app/client/[slug]/**`); on
#197/#198/#199 the check never runs at all.

So carrying #230 into those three would have inflated three diffs with a merge
commit for a check that cannot fire — and, worse, an accidental no-op (receipt #12)
is what revealed it. Read the workflow's `on:` block before concluding a PR is
blocked by a check: absent ≠ red, and non-required ≠ blocking.

## 14. "The user merged things" is the normal cause of a same-night re-conflict

**Verified 2026-08-21 (run 2).** Five skills-repo PRs that run 1 had driven to
`MERGEABLE/CLEAN` at ~03:15Z were all `CONFLICTING` again by 09:32Z. Cause: #29,
#30 and #31 landed on `main` between 05:17Z and 06:28Z. Not a regression, not a
bad resolution — just a moved base.

The deeper finding is structural and worth surfacing rather than re-fixing nightly:
every branch in that repo commits regenerated `MANIFEST.yml` and `README.md`, so
**every branch conflicts with every other branch and with main**, on the same paths,
forever. A sweep that re-resolves this each night is treating a design choice as
weather. Name it in the digest and let the user decide (generate at merge time / in
CI, or keep committing them and accept the tax) — do not quietly keep paying it.

## 15. The gate command itself was broken, so every "not green" was the command failing

**Verified 2026-09-29:** SKILL.md's ready gate was
`gh pr checks <n> --json name,state,conclusion | python3 bin/receipts-check.py …`.
`gh pr checks --json` has no `conclusion` field. It printed `Unknown JSON field:
"conclusion"` to stderr and nothing to stdout, and the checker then saw an empty
rollup and exited 1 on EVERY PR. Real green PRs (one in each of two libraries)
looked "not green". Four separate diagnosis agents found it independently in one sweep.
The field is `bucket` (`pass`/`fail`/`pending`/`skipping`); the checker reads `state`,
so the fix was the field list only. Rule: a gate whose failure mode looks exactly like
its verdict must be run once against a known-green PR before anyone trusts it.

## 16. A cancelled check is not a green one — and neither gate looked

**Verified 2026-10-05:** a /wrap flipped two PRs (an app repo, a routine library) ready
while five and one of their CI jobs, respectively, were CANCELLED: GitHub's hosted
runners never picked them up ("The job was not acquired by Runner of type hosted even
after multiple attempts", 19:33–20:18Z). The draft check passed (nothing was a draft) and
`receipts-check.py` passed (named checks existed; by design it does not judge
conclusions). The user opened their queue and found nothing actually ready to merge.
Fix: `bin/prr.sh` judges conclusions per ready PR against the base branch's latest run
of each check. Re-running the workflow (`gh run rerun <id>`) turned both green with
no code change.

Its first live run also found a true positive outside this session: an app repo's
`staging` → `main` prod promotion PR is red on `audit` while `main` is green, so it
would carry `staging`'s critical `next` advisory into prod. "Inherited" is relative
to the PR's own base, which for a promotion is `main`, not `staging`.
